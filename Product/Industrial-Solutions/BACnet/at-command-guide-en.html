EOE-W55RP20_BACnet Module AT Command Guide

This is the reference for the commands with which a host MCU configures the EOE-W55RP20_BACnet module over UART, puts values into BACnet objects, and receives writes that come from the network.

Firmware 1.0.0. 56 commands (including the bare AT). The B/IP-only build lacks the 7 marked [SC] and has 49.

3. Syntax and rules​

3.1 Port​

ItemValue
Portuart1 (GP4 TX / GP5 RX, GP6 CTS / GP7 RTS)
Serial settingsDefault 115200 8N1, no flow control. Changed with AT+UART
Line endingCR, LF and CRLF are all accepted. Responses always end with CRLF
Line length255 bytes maximum (not counting the terminator). A longer line is not executed: ERROR:BUFFER_TOO_LONG
Arguments12 maximum

The console log goes out separately on uart0 (921600). No log mixes into the AT port.

When boot finishes, +READY:"<version>" is sent (§14). Send commands after it.

3.2 Forms​

AT                       check the module answers → OK
AT+NAME=<args>           set
AT+NAME?                 query
AT+NAME                  execute (action without arguments)
AT+NAME=?                test — OK if there is a set or execute form, ERROR:INVALID_COMMAND if query only

  • Command names and keywords are case-insensitive (at+bacmode=bip works). The exception is the confirmation word "CONFIRM" (AT+FACTORY · AT+BMAPCLEAR) — it must be in capitals exactly as written.

  • Enclose string arguments in double quotes. A comma inside quotes is not a separator. There is no escape for putting a double quote inside quotes. Only one pair of quotes, at the two ends, is stripped from an argument, so with an even number of quotes an inner " is not refused but stored as it is (AT+BOBJADD=AI,1,"say "hi"",62 gives the name say "hi"). With an odd number, the commas after it are read as inside the quotes too and the arguments shift. A query outputs the name inside quotes without escaping — do not use " in a name (AT+BOBJ?).

  • Most numbers accept both decimal and 0x hexadecimal (instances, state counts, vendor id, ports, TTL, lengths and so on). A leading 0 is plain decimal — 047808 is 47808 (it is not read as octal). Some places take decimal only — the object-side values, which use the same parser as the CSV.

    PlaceGiven 0x
    The type number of AT+BOBJADD · AT+BOBJDEL · AT+BOBJVALTYPE_MISMATCH (0x2 is read neither as a type name nor as a number)
    The analog Units number of AT+BOBJADDINVALID_PARAMETER
    The multi-state and binary values of AT+BOBJVALINVALID_PARAMETER

  • AT+NAME=? is the test form (3GPP 27.007). It does not execute the command; it only answers whether the command has a form that takes arguments (set or execute). An execute-only command answers OK too — AT+REBOOT=? · AT+BMAPRELOAD=? answer OK and neither reboot nor re-apply. A query-only command (AT+BOBJ=?) gives ERROR:INVALID_COMMAND. AT+FACTORY=? · AT+BACPASS=? do nothing either.

  • More arguments than the command can take at most are refused. AT+IP="1.2.3.4",5 is ERROR:INVALID_PARAMETER — the command is not half-applied with an OK. A command that takes a different number of arguments in different forms is counted per form — a surplus argument on the TCP_SERVER or UDP form of AT+SOCKOPEN (AT+SOCKOPEN=2,UDP,6000,9) also opens nothing and is INVALID_PARAMETER.

  • A value that does not read as a number (a negative number in an unsigned place included) is INVALID_PARAMETER. In an unsigned place the first character must be a digit — a leading space and a + are refused as well (AT+BIP= 47808 · AT+BIP=+47808). The web's Product ID is judged the same way (AT+PRODUCTID). A number out of range is INVALID_PARAMETER or VALUE_OUT_OF_RANGE depending on the command, but either way it is never truncated, wrapped or corrected. A 32-bit value is checked before it is narrowed — AT+BOBJDEL=AI,4194304 never ends up pointing at a different object.

  • Port numbers are the same in every command — 1 … 65535; outside that, VALUE_OUT_OF_RANGE (BIP · BIPFD · SOCKOPEN · SOCKSENDTO · SOCKPEER).

  • A query must end at ?. AT+BOBJ?x · AT+VERSION? (with the trailing space) are ERROR:INVALID_PARAMETER. No query takes arguments.

  • An empty position and an empty string are different. A position left empty, with only its comma, means "not given" — AT+BSCHUB=,"wss://b" leaves the primary as it is (exception: AT+BACVENDOR clears an empty position too). A bare "" means "an empty value was given", and in a field that can be emptied it means "clear it" — AT+BACDEV=5,"" returns the name to the derived value, and AT+TIMESRC=BACNET,"" clears the SNTP server. A "" given to a field that cannot be empty (the broadcast method of AT+BIP, the fourth position of AT+BOBJADD, the value and status of AT+BOBJVAL) is refused. The fifth position (flags) of AT+BOBJADD takes "" as "no flags" as well.

  • There is no command that lists the command table.

3.3 Responses​

Every command ends with a single OK line on success or ERROR:<code> on failure (§16). Queries and some set commands send one or more +NAME:... lines before that.

AT+BIP?
+BIP:47808,SUBNET,192.168.0.100,192.168.0.255
OK

URCs (§14) are serialized through the same transmit path and can come before or after a command's response. A host that reads line by line tells them apart by the +NAME: prefix. Where a query response and a URC could take the same shape, they have been made different on purpose — +BIPFD:STATE,… / +BIPFD:CONFIG,… are query responses, +BIPFD:REGISTERED,… / +BIPFD:FAILED,… are URCs, and +TIME: has 4 fields as a query response and 3 as a URC.

3.4 Binary mode​

AT+SOCKSEND · AT+SOCKSENDTO · AT+BSCCERTW declare a length first, then accept exactly the declared number of bytes of raw data after the > prompt (no line break).

AT+SOCKSEND=0,5
> HELLO
+SOCKSEND:0,5
OK
  • In this phase CR, LF, NUL and even the string "AT" are all data.
  • No line break follows the prompt, so in the bytes the module sends, the result arrives on the same line as the prompt, as in > +SOCKSEND:0,5. A host that reads line by line should recognize the prompt as the two bytes > and strip the > from the front of the result line.
  • The time limit is an absolute 10 seconds from when the prompt is sent (not an idle time). Even if bytes are still arriving, the command ends with ERROR:PAYLOAD_TIMEOUT after 10 seconds.
  • The maximum length accepted at a time is 1460 bytes (sockets) and 1024 bytes (AT+BSCCERTW).
  • End command lines with CRLF. A single LF byte right after a CR is dropped as the other half of the line ending. So when a host that ends lines with CR alone sends a payload that starts with LF (0x0A), that first byte is lost — the module cannot tell it apart from the byte stream of a CRLF host.
  • A refusal after the prompt makes the data the host sent go to waste. So everything that can be known is checked before the prompt — the channel state, the destination, the length, the offset of a credential upload.
  • On a port configured for 7 bits or XON/XOFF, the transfer is refused before it starts (ERROR:NOT_SUPPORTED). Those two settings silently corrupt data (AT+UART).
  • The payload of AT+BSCCERTW (which may be a piece of a private key) is wiped from the receive ring, the line buffer and the payload buffer right after it is processed.

AT+OTAFWUP also accepts raw data but does not declare the length in advance: the firmware package carries its own size in its header, and that header is itself the front of the stream. The only difference is that it is the module, not the host, that knows where the end is; everything else is the same.

3.5 When settings are saved — most settings take no effect until AT+SAVE​

Set commands change only the settings in RAM. Writing them to flash and actually applying them is done by AT+SAVE. The exceptions are the two tables below — commands that act without a save, and settings that AT+SAVE stores but whose value in RAM is read right away.

AT+BACMODE=BIP
AT+BACDEV=1001,"AHU-3"
AT+BIP=47808
AT+SAVE

This is so that the datalink, the instance and the port are applied in one go. Applied command by command, the datalink would restart once per command, and clients would see a half-changed device in between.

  • BACnet settings have no effect on the network before they are saved. Even after AT+BACDEV · AT+BACVENDOR are changed, Who-Is · I-Am · ReadProperty answer with the old values until the save. A reset without saving loses the settings, but no client has ever seen those values.
  • Most queries answer the configured value (the value the next AT+SAVE will apply). A command that also has a separate value in operation now shows it as well — RUNNING|STOPPED in AT+BACMODE?, the APPLIED line of AT+BACDEV?, the last two fields of AT+BIP?, the STATE line of AT+BIPFD?, ACTIVE|PENDING in AT+UART?.
  • AT+UART takes effect only after a reboot, even once it is saved.

4. Device — device control, storage, diagnostics​

AT — check the module answers​

AT
OK

AT+SAVE — the commit point​

AT+SAVE
OK

Writes the settings to flash and applies them (§3.5), in this order:

  1. PERSISTENT values first. Any Present_Value the journal's rate limit (10 seconds per object) has been holding back is written now — so that no value is lost if power fails after the "save".
  2. The object table is folded into the mapping. Without this, definitions made with AT+BOBJADD would be gone at the next boot. The folding and the writing happen under one mapping lock, so a web CSV import cannot change the table in between.
  3. The whole configuration is written to the A/B slots.
  4. It is applied — only the settings that actually changed. Network (only when the address differs from the chip's — all sockets close and the services come back up) → BACnet → web, in that order. Saving after changing only the object mapping does not cut the AT channels.

BACnet is applied by the BACnet task in its next cycle (at most 20 ms). The OK comes first, and an AT+BACMODE? right after it may show STOPPED for a moment (with SC, several seconds, through the TLS handshake). What is applied: the mode · B/IP port and broadcast method · FD registration · hub URIs and timers · instance and name · Vendor text · time source · UTC offset · certificate-period check policy · DCC/RD password, and only what changed is restarted. When the instance or the name changes, I-Am is broadcast again and Database_Revision goes up by 1.

  • If the save succeeded and only the apply failed, the answer is OK and a warning is left on the console. The stored settings are already right and are used at the next boot — telling the host to save again would be the wrong advice. If the network apply fails, the module keeps running on the previous address and the services come back up on that address. Whether the address actually changed is told by +IPCHANGED — if it did not come, the address did not change.
  • If the save itself fails, the answer is ERROR:<code> and nothing is applied: STORAGE_BUSY if another operation is using the storage (try again), MAPPING_TOO_LARGE if the object mapping does not fit in the configuration slot, STORAGE_FAILURE for a write failure in which the slot written to flash does not read back, and INTERNAL for any other failure (a factory reset in progress and so on). In every case the previous slot is left as it was.
  • If the stored object mapping could not be read at boot (logged on the console), step 2 is skipped and the stored table is protected. In that state AT+BOBJADD · AT+BOBJDEL are refused from the start with ERROR:STORAGE_FAILURE, so an edit that could not be stored never gets an OK.

AT+REBOOT​

AT+REBOOT
OK

After the response has gone out, it first writes the PERSISTENT values the journal's rate limit was holding back, closes everything in the order AT channels → persistent services (B/IP · SC hub connection · web), waits 200 ms, stands the watchdog down and reboots. Peers receive a FIN. With an immediate reset, every peer would hold on to a dead connection until its own timeout.

Each channel is waited for up to 200 ms only — a channel that is resolving a name or connecting for AT+SOCKOPEN (up to about 11 seconds) is not closed but left to the reset (only that peer gets no FIN). This is because the restart of ReinitializeDevice takes this path on the BACnet task, and the wait must not run past the watchdog's supervision (4 seconds). The web's Reboot and the restart after an OTA are the same.

At the next boot +DIAG:RESET is SOFTWARE, and the Device's Last_Restart_Reason is COLDSTART.

AT+FACTORY — factory reset​

AT+FACTORY="CONFIRM"
+FACTORY:COMPLETE

The module reboots right after +FACTORY:COMPLETE (no OK comes).

AT+FACTORY="CONFIRM"
+FACTORY:ERROR,CREDENTIALS
ERROR:STORAGE_FAILURE

If the credential slots cannot be erased, nothing is reset and the module does not reboot. It tries the erase once more, and if that fails too the command ends with +FACTORY:ERROR,CREDENTIALS and ERROR:STORAGE_FAILURE — a reboot with the private key still in place would look like a completed factory reset. Try again. If it keeps failing, the flash is faulty. From then until a reboot, credential upload and delete answer STORAGE_BUSY. Until the reboot AT+BSCCERT? shows every item ABSENT, but that does not mean the key is gone — the erase failed, so it may still be in flash.

Erase order:

  1. BACnet/SC credentials — the two slots that hold the private key, certificate and CA are erased (erased, not overwritten). This comes first so that, even if the reset is cut off midway, the most important part (destroying the private key) is already done. The B/IP-only build erases the same area too — the board may hold credentials an SC build put there.
  2. The whole configuration — to the defaults below.
  3. The object mapping and the runtime journal — host object definitions and PERSISTENT values. Database_Revision is not reset but keeps counting (going backwards would fool clients that cache).
  4. The stored object CSV (when the staging area holds a CSV).

The refusals are the same too: whichever path is used, +FACTORY:ERROR,CREDENTIALS or +FACTORY:ERROR,OTA_PENDING goes out on the AT port — FAC_RSTn has nobody to answer, so this URC is the only news the host hears, and while the pin is held the reset is tried again every 5 seconds. The web answers 200 only after the credentials have been erased; a failure is 500 Credential Erase Failed, and a staged image is 409 Firmware Update Pending.
  • "CONFIRM" must match exactly, including case. Anything else is ERROR:INVALID_PARAMETER.

It outputs some twenty lines at a time. The fields of each line and the matching web values are in §15. The order of the lines:

  • The BACnet lines are output whatever the mode (OFF included), with zeros if need be. "Nothing has arrived" is the answer to "are clients reaching the device", and a line that appears only when something happens cannot give that answer.
  • Fields are only ever added at the end of a line. The positions of the earlier fields do not change, so a parser written for an older line still reads it. RESET is always last.
  • The counters are copied without a lock, so two numbers on one line can be one request apart. For diagnostics that does no harm.

All four are required. If one could be left out, a value the operator did not choose would come along with it, and the four values are not independent of each other — 7 bits with no parity and 8 bits with even parity are entirely different decisions.

Parity and flow control are given by name (case-insensitive). An unknown name does not fall back to the default; it is refused, because the default here is a setting that drops bytes.

Stop bits are not configurable. They are always 1.

The four kinds of flow control​

ValueWhatDirection
NONENone—
RTSCTSHardware. GP6 (CTS) / GP7 (RTS), handled directly by the PL011Both
DTRDSRGPIO. Watches DTR on GP8Module transmit only
XONXOFFIn-band. 0x11/0x13Both

DTRDSR is one-sided. When the host lowers DTR, the module stops transmitting. There is no reverse direction — DSR (GP9) already means "module ready", and if the module lowered it because its receive buffer was full, a host that reads DSR as the ready signal would read a busy module as a dead one. If both directions are needed, use RTSCTS. RTS/CTS on GP6/GP7 and DTR/DSR on GP8/GP9 are different pins and different signals.

With RTSCTS, while the host holds CTS, the module's transmission sleeps until the FIFO empties — meanwhile the web, DHCP, SC and link supervision keep running. After 5 seconds it reports once on the console. Lines that pile up while transmission is held are dropped once the transmit queue (8 entries) is full, and counted as dropped in +DIAG:ATTX.

XONXOFF is software. The module stops transmitting when it receives 0x13 (XOFF) and resumes on 0x11 (XON). In the other direction, it sends XOFF when the free space in its receive ring buffer (1024 B) falls below 1/4, and XON when it recovers above 1/2. These two bytes are not passed to the parser.

Two settings cannot carry binary payloads​

7 bits and XONXOFF block AT+SOCKSEND · AT+SOCKSENDTO · AT+BSCCERTW · AT+OTAFWUP.

5. Network — addressing​

AT+NETMODE — address assignment​

AT+NETMODE=DHCP
AT+NETMODE=STATIC
AT+NETMODE?          → +NETMODE:STATIC

The factory default is STATIC (the table under AT+FACTORY). The words are case-insensitive — so is mode on the web Network tab.

How DHCP behaves. The lease is renewed at T1 (half the lease if the server gives none). If a renewal gets no answer, the module waits and asks again: before T2 (7/8 of the lease) it waits half the time left until T2, and after T2 half the time left until the lease expires — but always at least 60 seconds (RFC 2131 4.4.5). If the server refuses the renewal (NAK), the module drops that address and starts negotiating from the beginning at once. If the address received is different, the channels are cut with ADDRESS_CHANGED and +IPCHANGED is sent. When the link goes down the lease is released at that moment, and when the link comes back negotiation starts again at once. A failed negotiation and a lease that fails to apply are retried at intervals starting at 1 second and doubling up to at most 64 seconds. A DHCP response that arrives right after STATIC is saved is discarded — it does not overwrite the stored address.

AT+IP · AT+MASK · AT+GW · AT+DNS​

AT+IP="192.168.0.100"
AT+MASK="255.255.255.0"
AT+GW="192.168.0.1"
AT+DNS="8.8.8.8"

AT+IP?               → +IP:"192.168.0.100"

Set and query look at different things. Set writes to the stored settings; query reads the value the chip is using now. Under DHCP the two differ for good — the leased address is not written to the settings. If it were, the next AT+SAVE would freeze the temporary address into the STATIC settings, and switching back to STATIC would leave the user with an address they never chose. The configured values are given by cfg_ip · cfg_mask · cfg_gw · cfg_dns in the web's /api/status — these are the settings in RAM, so they include edits such as AT+IP= that have not been saved yet (they may differ from the stored values).

Only AT+DNS? answers the value the resolver holds, because the DNS server is used by the firmware, not by the chip. Name resolution for hub URIs, the BBMD, the SNTP server and socket channel host names uses this server.

The resolver accepts only responses from this server's address and UDP port 53 (a random ID for each query). A DNS server that answers from a different address or port (some behind NAT, servers with several addresses) has its responses discarded and the name does not resolve — in that case, give the address the responses come from with AT+DNS. Each name is asked twice, 3 seconds each.

Only the format is checked. Only a value that does not read as dotted-quad notation is ERROR:INVALID_PARAMETER; any address that reads is accepted and put into the chip at AT+SAVE — 0.0.0.0, broadcast and multicast IPs, a mask that is not contiguous or is 0.0.0.0, and a gateway outside the subnet are not refused either. One typo can leave the module unreachable over IP after the save. The way back is then the AT port. Before saving, check the four values again by hand, not by query (the query gives the chip's current values).

Under DHCP the lease's DNS comes first. Every time a lease is received, the resolver switches to the DNS server the lease gave (DHCP option 6). If the DHCP server gives no DNS option, the stored DNS (AT+DNS followed by AT+SAVE) is used — the names of hub URIs, the BBMD and the SNTP server are resolved with that server. An AT+DNS that has not been saved does not go into the resolver, even when the lease is renewed. AT+SAVE in DHCP mode does not re-apply the address, but if the current lease has no DNS it puts the stored AT+DNS into the resolver at once (channels are not cut). The web locks the address fields under DHCP, so on the web the DNS saved while in STATIC becomes this fallback server. Check the server the resolver actually uses with AT+DNS?.

Caution — when a save cuts the channels. When AT+SAVE re-applies the chip's address, every open socket descriptor is closed. AT channels receive +SOCKDISCONNECTED:<ch>,NETWORK_RECONFIGURED and, by design, are not recovered automatically, so the host reopens them. BACnet recovers by itself — the B/IP socket reopens on the new address (the broadcast address is recomputed too), FD registration starts again from the beginning, and SC reconnects to the hub. The new address is announced by +IPCHANGED (§14).

When a re-apply is refused. If a connection that is closing (a web browser that did not read its response to the end, for example) does not let go of the chip's socket within 1 second, the chip does not take the new address. The module brings the services back up on the old address and re-applies the saved STATIC settings up to five times, 3 seconds apart. Each re-apply cuts all channels as above (+SOCKDISCONNECTED:<ch>,NETWORK_RECONFIGURED), logs the web out and reconnects SC to the hub, so a channel reopened in between can be cut too. +IPCHANGED comes only when the address was actually applied — after changing the address, wait for it before opening channels. If all five are refused, no URC says so: if +IPCHANGED does not come within a little over 20 seconds, the address was refused, and channels can be opened on the old address. The settings are applied at the next reboot — or at the next AT+SAVE, even one that changes nothing in the network (the saved settings differ from the chip's, so that save re-applies them and the channels are cut). AT+SAVE answers OK in every case, since the save itself completed. If applying a DHCP lease is refused, the DHCP client retries by itself.

AT+BIPFD="bbmd.example.com",47808,300
AT+BIPFD="10.0.5.1",47808,600
AT+BIPFD=0                         stop registering
AT+BIPFD?
  +BIPFD:STATE,REGISTERED,287
  +BIPFD:CONFIG,1,"bbmd.example.com",47808,300

Registers with a BBMD so that a device on a subnet with no BBMD can be found and read from other subnets (Annex J.5). While it is registered, this device's broadcasts are also sent to the BBMD as Distribute-Broadcast-To-Network.

ArgumentValue
bbmdAn IPv4 literal or a DNS name (letters, digits, -, .), up to 63 bytes, without :port. Longer is BUFFER_TOO_LONG; a wrong format, INVALID_PARAMETER
portThe BBMD's UDP port, 1 … 65535
ttlThe requested Time-to-Live (seconds), 1 … 65535. Outside, VALUE_OUT_OF_RANGE. The registration is renewed every half TTL

All three are taken together. A registration is one statement, and a TTL left over from another BBMD is not a value the operator chose. AT+BIPFD=0 is the only number that turns it off (any other single number is INVALID_PARAMETER). After it is turned off, the BBMD address stays in the settings so the query shows what was used, and the registration on the BBMD side disappears by itself when the TTL runs out. Applied at AT+SAVE; registration starts over only when the settings actually changed.

The query has two lines.

+BIPFD:STATE,<state>,<seconds left>[,<reason>[,0x<code>]]
+BIPFD:CONFIG,<0|1>,"<bbmd>",<port>,<ttl>
StateMeaning
OFFRegistration is off, the mode is not BIP, the B/IP socket is closed, or the module is waiting for the Ethernet link
RESOLVINGLooking up the BBMD name (on the system workqueue — it does not block the BACnet task). An IPv4 literal skips this step
REGISTERINGRegister-Foreign-Device sent, waiting for the BVLC-Result
REGISTEREDRegistered. <seconds left> is the time until the BBMD deletes the entry if no renewal reaches it
FAILEDFailed. Retried at intervals that start at 64 seconds and double, up to the TTL (but no more than 10 minutes)

FAILED carries a reason — DNS (the name did not resolve), TIMEOUT (no answer from the BBMD), NO_SOCKET (no B/IP socket), NAK (the BBMD refused; the BVLC-Result code follows — usually 0x0030). When the B/IP socket closes during registration and the state becomes OFF, a reason is attached as well: +BIPFD:STATE,OFF,0,NO_SOCKET. The second line holds the configured values.

Why the first line starts with STATE: otherwise a registered module's query response +BIPFD:REGISTERED,<seconds left> would have the same shape as the registration URC +BIPFD:REGISTERED,<ttl>, and a host reading line by line could not tell a query response from a new registration. No URC starts with STATE or CONFIG.

With no Ethernet link, registration is neither started nor sent. Booting with a static address, the B/IP socket opens at about 0.3 seconds but the PHY link comes up at about 2 seconds. Meanwhile the state stays OFF, neither the name lookup nor Register-Foreign-Device goes out, and nothing is counted as a failure (no retry interval is used either). If the link drops during registration, the remaining transmissions wait for the link and carry on as soon as it comes up. If the BBMD's TTL runs out while there is no link, that is a real expiry, so it is FAILED,TIMEOUT.

A +BIPFD URC goes out when the state changes (§14). The counters are in +DIAG:BIPFD.

8. SC — BACnet/SC datalink​

Used when AT+BACMODE=SC. Every command in this chapter is [SC] — the B/IP-only build does not have them, so they get ERROR:INVALID_COMMAND. The web UI's BACnet/SC tab (/api/bacnet/sc, /api/bacnet/sc/status, /api/bacnet/sc/cred) does the same work.

The module is a hub connector (Annex AB). It has no hub function and no direct connections. The connection is built on one hardware TCP socket of the W5500, in the order TLS 1.3 (mutual authentication, EC P-256) → WebSocket (hub.bsc.bacnet.org subprotocol) → BVLC-SC Connect-Request.

Order of preparation

AT+BSCCERT=KEY,<length>   + AT+BSCCERTW ...   device private key        (§8 AT+BSCCERT)
AT+BSCCERT=CERT,<length>  + AT+BSCCERTW ...   device operational certificate
AT+BSCCERT=CA1,<length>   + AT+BSCCERTW ...   issuer of the hub's chain
AT+BSCHUB="wss://hub.example.com:4443"        hub URI
AT+BACMODE=SC
AT+SAVE                                       → +BSC:CONNECTED,PRIMARY

Credentials need no save (they are written the moment they are uploaded); the URI and the mode are applied at AT+SAVE.

How the hub connector behaves

  • One connection at a time. It always tries the primary first and, if that fails, the failover at once. If both fail, it waits the reconnect delay and starts again from the primary. The delay starts at the minimum reconnect time, doubles with every failed round up to the maximum reconnect time, and goes back to the start on reaching CONNECTED.
  • While attached to the failover, it probes the primary with a TCP connection only, once every maximum reconnect time (a momentary second socket, no TLS). If the connection opens, it sends a Disconnect-Request to the failover and moves to the primary. If the probe or the primary session fails, the interval doubles, up to 8 times the maximum reconnect time.
  • Heartbeat. While connected, if nothing has been received (or sent) for the heartbeat time, it sends a Heartbeat-Request, and if nothing is received for twice that time, the connection is taken as lost (HEARTBEAT).
  • The VMAC is drawn at random once when the SC thread starts (low nibble of the first octet 0x2, locally administered · unicast) and kept across reconnections. It is drawn again only when the hub refuses with NODE_DUPLICATE_VMAC (up to 3 times per round). The Device UUID is a name-based UUID (version 5) made from the factory MAC, so it stays the same for the whole life of the device.
  • When the connection is made, an I-Am is sent. When the mode leaves SC, or the URIs, timers or credentials change, the connection is closed politely with a Disconnect-Request.

AT+BSCCERT — credential upload, delete, query​

AT+BSCCERT?                                     what is stored
ItemContentRequired
KEYDevice private key — EC P-256, SEC1 or PKCS#8, unencrypted PEM or DER●
CERTDevice operational certificate — an EC P-256 X.509 whose public key is that of KEY●
CA1The issuer certificate the hub's certificate chain must lead to●
CA2A second issuer (optional) — for a CA changeover period or an intermediate CA
  • One item is up to 4096 bytes in the form it is uploaded in (PEM or DER). Longer is BUFFER_TOO_LONG; 0 is INVALID_PARAMETER. It is stored as DER, and the DER of the four items together must fit in one 8 KiB slot (if it does not, BUFFER_TOO_LONG at the last chunk).
  • Starting opens a place to receive the AT+BSCCERTW chunks. Nothing is stored until the last chunk has arrived and passed verification. Starting discards a previous upload this port had open — a host that loses its way midway can simply start again from the beginning.
  • ABORT only gives the place back, without starting an upload. Use it to let a web upload or a DEL use the place. An upload with no chunk for 60 seconds is discarded when the other side (a web upload · DEL · the start of another item) asks for the place.
  • DEL is STORAGE_BUSY while an upload is open (ABORT first). An upload with no chunk for 60 seconds, however, does not block it — DEL discards that upload and deletes. A failed flash write is STORAGE_FAILURE.
  • DEL of an item that is not stored is OK too (not OBJECT_NOT_FOUND), because "that item is not there" is the result asked for. Whether it was there is seen with AT+BSCCERT?.
  • No save (AT+SAVE) is needed. A completed upload and a delete are written on the spot to the credential area (two slots, A/B; if power fails during a write, the previous credentials remain), and the hub connector reconnects with what changed. AT+FACTORY erases both slots.

Key and certificate pair. A new CERT that does not match the stored KEY is refused (CRED_MISMATCH — it is a certificate that cannot be used). A new KEY, on the other hand, is accepted even if it does not match the stored CERT — to change both, one of them has to be uploaded first. In between, the pair shows as MISMATCH and the hub connector does not dial (CREDENTIALS). That clears when the matching CERT arrives.

The private key is never exported in any form. The KEY line says only that it is there, its type and its pairing — no length, no hash, no value computed from the key. The web's /api/bacnet/sc/cred gives the same three things only. Whether a certificate's period is valid now is judged by the hub connector with the BACnet clock.

CN notation. The subject and issuer CNs are someone else's characters inside the certificate, so they are converted on output so as not to break the line — every byte outside 0x20 … 0x7E, and quotes and backslashes, become ?, and they are cut at 63 bytes. So a non-ASCII (UTF-8) CN, Korean for example, shows as a run of ?, and a long CN is cut. When a host compares with a certificate it holds, it compares the SHA-256 fingerprint, not the CN.

"No upload open" is judged from the upload state the AT port remembers on its own side. Once 60 seconds have passed without a chunk and the store has given the place to the other side (a web upload · DEL), the AT port does not know that, so it refuses with INVALID_PARAMETER only after giving the prompt and receiving the bytes — that chunk is discarded. Start an upload that stopped for more than 60 seconds again with AT+BSCCERT=<item>,<length>.

When an answer is lost. The offset must continue from what has been received or be a repeat of the previous chunk. If no OK came, send the same chunk again (same offset, length and bytes) — the store checks that the bytes are the same and accepts it. A repeat of the last chunk, the one that completed the item, gets the first answer again (STORED or the refusal). If the store changed in between (a web upload or delete) or the host sent a different AT+BSCCERT=, it is INVALID_PARAMETER.

The last chunk can take a while. The completing chunk is converted to DER, verified and written to the slot on the spot. If the SC thread is in the middle of a cryptographic operation, the store waits up to 15 seconds for that step to end, and the slot erase comes on top. The host should wait 20 seconds or more for the answer to the last chunk. Meanwhile the AT port answers no other command.

The received bytes (which may be a piece of a private key) are wiped from the receive ring, the receive buffer and the payload buffer right after processing, and the store's staging buffer is wiped too on completion or cancellation.

The web UI uploads an item in one go, through the same checks (POST /api/bacnet/sc/cred?item=…).

The host MCU owns the objects. The module shows the objects the host defined on the BACnet network, the host puts in the values with AT+BOBJVAL, and writes from the network are passed to the host as +BACWRITE (§14). The Device and the Network Port are fixed objects the module holds itself.

  • Up to 256 objects (the Device and the Network Port not counted), and up to 64 priority arrays (commandable objects) (both fixed at build time).
  • Many objects are defined at once with a CSV on the web UI's Object mapping tab. AT has only AT+BMAPRELOAD, which re-applies the stored CSV, and AT+BMAPCLEAR, which clears it. It is not guaranteed to go up by 1 at a time — AT+BMAPCLEAR raises it twice, and a re-apply that discards a failed import or unsaved edits raises it too. Changes an Input's reading or a Value object's value at once. COV subscribers get a notification when the change exceeds the COV_Increment or the Status_Flags change, and a PERSISTENT object is recorded in the journal (once per object per 10 seconds — changes in between are merged into the next record and counted in +DIAG:BACSTORE; see "PERSISTENT values and power loss" below).

PERSISTENT values and power loss. Journal records are limited to one per object per 10 seconds (a build option, 1 second … 1 hour). WriteProperty has no authentication, so if a client that changes a writable PERSISTENT value without pause were allowed one record per datagram, the journal flash would wear out within a few weeks. This limit applies equally to AT+BOBJVAL and to WriteProperty · WritePropertyMultiple from the network.

  • An object that has had no record since the previous 10-second tick has its first change recorded at once.
  • Further changes within the same period stay in RAM only, and at the next 10-second tick only the last value is recorded. The values in between are already visible on the network, and the OK (AT) or SimpleACK (WriteProperty) has already gone out.
  • So even a value that was answered may be missing from flash for up to about 10 seconds. If power is cut, or a reset-pin or watchdog reset comes, in that time, the object returns after the reboot to the last value recorded. Example: if 271 is written and 272 right after it, and power is cut before the next tick (or during the tick's write), the value after the reboot is 271, even though both writes were answered. Values are never mixed or corrupted — a record cut off mid-write is skipped and the complete value before it is used.
  • Waiting values are written by AT+SAVE, AT+REBOOT, AT+OTAREBOOT, the web's restarts (reboot button · automatic restart after an update) and ReinitializeDevice, before any restart. A power cut, the reset pin and a watchdog reset give no such chance.
  • If a value must survive and power may be cut soon (the host knows of a power cut in advance, for example), wait at least 10 seconds after the last write, or send AT+SAVE. AT+SAVE also rewrites the whole configuration, so it is not meant to be called after every value.
  • The number of merged changes is the second field of +DIAG:BACSTORE.

AT+BWRACK — answer a confirmed write​

+BACWRITE:17,AO,1,8,42.5          ← URC: a client wants to write 42.5 to AO,1 at priority 8
AT+BWRACK=17,OK                   approve → commit, SimpleACK to the client
AT+BWRACK=17,VALUE_OUT_OF_RANGE   refuse → Error PROPERTY / VALUE_OUT_OF_RANGE to the client

A remote Present_Value write to an F (CONFIRMED) object asks the host before it is committed. The module does not wait — it keeps the request in a pending slot (there are 4) and goes on handling the next requests, and the answer goes out when AT+BWRACK arrives or the deadline passes.

ArgumentValue

10. Time — clock and time source​

The module has no RTC. The clock is computed from the time received from the network and the time elapsed since, and after a reboot it is "unknown" again. It gives neither 1970 nor a guess — while the time is unknown, the Device's Local_Time · Local_Date are encoded as unspecified. A synchronization that gives a time earlier than 2026-01-01 is refused and counted.

Where the clock is used: the Device's Local_Time · Local_Date · UTC_Offset · Time_Of_Device_Restart, and the period check of SC certificates (AT+BSCVALIDITY). On the web it is the time section of the BACnet tab (GET/POST /api/time).

SNTP opens one socket on the system workqueue, asks, and closes it (it does not block the BACnet task). On failure it asks again at intervals that start at 64 seconds and double, up to the interval. Only a response that returns the request's random transmit timestamp is accepted (forged or stale responses and unsynchronized servers are counted as bad replies). With no Ethernet link, it does not ask. The first query comes 2 seconds after the network comes up, and in a static-address boot the PHY link comes up at 1.8 to 2.5 seconds, so that query can come before the link. Then it waits for the link and asks — this is not counted as a failure, and there is no +TIME:SNTPFAIL and no 64-second retry interval.

When the clock is set for the first time or the side that set it changes, +TIME:SYNCED goes out; when SNTP turns to the failed state, +TIME:SNTPFAIL goes out (§14). The counters are in +DIAG:TIME · +DIAG:SNTP.

If the SC certificate period refuses a BACnet time, that time is forgotten. In SC mode, a time received over BACnet came over the very connection now being judged, so a wrong time could block every reconnection — even the one that would bring the correct time. The connection ends, and the next dial proceeds with the clock "unknown". A time received by SNTP is kept. The number of times a time was forgotten is the forgotten field of +DIAG:TIME.

  • The range is ±1440 minutes (one day); outside, VALUE_OUT_OF_RANGE. A wrong text format (hours 1–2 digits, minutes exactly 2 digits and under 60) is INVALID_PARAMETER.
  • It means something with every time source, and with BACNET the operator must set it — it is the value that converts the local time of TimeSynchronization to UTC.   • Applied at AT+SAVE. Daylight saving time is not changed automatically.

11. Socket — TCP/UDP user channels​

TCP/UDP channels the host uses separately from BACnet. Logical channels 0 … 3. A channel number is a handle for the host and has nothing to do with the W5500's hardware socket numbers — hardware socket numbers are not exposed through any interface.

The maximum payload that can be sent at a time is 1460 bytes.

The W5500 has 8 hardware sockets, shared with BACnet, the web, DHCP, DNS and SNTP. When a channel is opened, one is kept back for system services, and one more if the stored mode is SC. How many can be opened now is answered by AT+SOCKAVAIL?.

AT+SOCKAVAIL? · AT+SOCKSTATUS?​

AT+SOCKAVAIL?

AT+SOCKSTATUS?
+SOCKSTATUS:0,TCP_CLIENT,ESTABLISHED,"192.168.0.20",5000,40001
+SOCKSTATUS:1,TCP_SERVER,LISTENING,"0.0.0.0",0,5001
+SOCKSTATUS:2,UDP,OPEN,"0.0.0.0",0,6000

<ch>,<mode>,<state>,"<peer address>",<peer port>,<local port> — only channels in use are listed. States: CLOSED OPENING LISTENING CONNECTING ESTABLISHED CLOSING OPEN ERROR.

  • The local port is the value the host gave. A TCP_CLIENT opened without a local port shows 0, not the ephemeral port actually in use (the 40001 in the example above is a case where one was given).
  • The peer address and port are the connection's peer; for UDP, the default recipient set with AT+SOCKPEER. AT+SOCKPEER given to a TCP channel changes only these fields (below).

A UDP channel is OPEN, not ESTABLISHED, because there is no connection to make; it sends normally in this state.

Data received over TCP is not discarded. If the peer sends faster than the host reads +SOCKRX, the module does not take the data out of the chip until there is room in the transmit queue — the chip's receive buffer fills, the TCP window closes and the peer slows down. Two slots of the queue are always kept for command responses and URCs. Room in the queue is reserved before reading, so even when several channels receive at once or a URC comes in between, no byte taken out of the chip is lost. A UDP datagram is discarded whole if there is no room — that is within a datagram's contract.

The web server handles requests one at a time. It takes the request being handled and one connection waiting behind it, and a third connection arriving in between is refused with a TCP RST. This is because only one socket listens on the web port, to save the 8 hardware sockets. Windows retries a refused connection a few times over a little more than 2 seconds, so it usually shows as a connection 0.5 – 2 seconds slower, and if it is refused in the end, WSAECONNREFUSED (10061). Linux and macOS clients get "connection refused" at once. The web page sends at most two requests at a time, so it does not hit this limit. When calling the web API from a script, send requests one at a time, and on a refused connection (ECONNREFUSED) or a reset (ECONNRESET) try again after a moment.

Password re-confirmation uses the same limit as login. The web's account change (/api/web), factory reset and DCC/RD password (/api/bacnet) ask for the current web password again, even within a session. A wrong password is counted together with login failures (0.5 · 1 · 1.5 · 2-second delays), and the fifth brings a 60-second lockout — meanwhile both login and re-confirmation get 429. The session that brought on the lockout ends.

The web's JSON accepts only three escapes inside strings: \" · \\ · \/. Any other escape (\u003e, \n and so on) makes the whole request refused with 400 — so that nothing is stored as a different string. Send text such as names, descriptions and passwords as plain UTF-8. The web page's JSON.stringify() escapes only control characters and unpaired surrogates (values these fields refuse anyway), so the page has no problem; match this when using the web API from another client.

There is no AT+WEBPASS?. Only a salt and a hash are stored, and neither ever leaves the device, so there is nothing it could honestly answer. The plain text is wiped at once, down to the line buffer. AT+BACPASS is the same.

13. OTA — firmware update​

There are two ways to put an image into the module — a web UI upload (Firmware tab, POST /api/ota/upload) and AT+OTAFWUP. The receiving side does not install. The received image is placed, verified, in the staging area, and the actual installation is done by the bootloader at the next boot. So whether the transfer fails, is cut off midway or is simply abandoned, the firmware running now stays as it is.

The staging area is the same place as the stored object CSV. Starting an OTA removes the stored CSV file (the applied object definitions stay in the settings). To use AT+BMAPRELOAD again, upload the CSV again.

Who causes the reboot differs. After a web upload the module reboots by itself — it answers the upload with {"staged":true,"reboot_in_s":5}, waits 5 seconds and reboots. If AT+OTACANCEL withdraws the image in that time, it does not reboot. On the AT path the host decides, with AT+OTAREBOOT (or any reboot) — so that the module does not take away from the host MCU the choice of when to tidy up its own state.

AT+OTAFWUP — send firmware over UART​

AT+OTAFWUP=<seconds>

<seconds> is the idle timeout. If not a single byte comes in for this long, the transfer is abandoned and the module returns to AT command mode. 1 … 600 seconds (outside, VALUE_OUT_OF_RANGE), with no default. Missing or not a number (AT+OTAFWUP, AT+OTAFWUP=x) is ERROR:INVALID_PARAMETER, and this refusal comes before the staging area is erased.

There is a reason this argument has no default. The value says "how quiet the host may be and still be normal", and that depends on where the package comes from. And this value is the only way out when the transfer is stuck. The module does not choose for you the means of getting the command port back.

Sequence — send it in one go​

AT+OTAFWUP=30
+OTAFWUP:READY                 ← staging erase done. Send the whole package now
<the entire .fwpkg file, as it is>
+OTAFWUP:IMAGE,1.0.0,408188    ← header accepted: version and image size
+OTAFWUP:DONE,408188,1.0.0
OK

There is no place to pause midway. After seeing +OTAFWUP:READY, push the .fwpkg through whole; the header is just the front of that stream. +OTAFWUP:IMAGE is a line reporting progress, not a prompt.

Wait for READY. On receiving the command the module erases the whole staging area (about 2 seconds). During the erase, interrupts are locked and reception itself stops, so anything sent in that time is lost from the UART FIFO. The only moment the host is sure to be quiet is this one, after sending the command and while waiting for the response, and that is why the erase is placed here.

With a terminal program​

After seeing READY, send the file as binary. If it fails, check with RXDROP in AT+DIAG? whether the host ran ahead.

Erasing comes first — and its cost​

The staging area is erased before the header is checked. In a stream, erasing after reading the header would mean erasing while the payload is already on the wire, and those bytes would be lost. So even a package that fails the check has already emptied the staging area. Not a single byte is written before the header passes, but what was there before (the stored CSV included) is gone.

No progress is reported during the transfer. Reporting progress would use the transmit queue, and when the queue is full, the very thread that is taking in the firmware stops. The amount received is told by the line that ends the transfer — +OTAFWUP:DONE on success, +OTAFWUP:ERROR,TIMEOUT,<received>,<total> on an idle timeout. After a timeout or a MAGIC refusal, AT+OTASTATUS? is IDLE · received 0 — that transfer is cleaned up as cancelled, so the amount received remains only in that TIMEOUT line.

When it looks stuck — do not type anything​

The module has not stopped. It is waiting for the rest of the package. In stream mode every byte typed is firmware data, and it also restarts the idle timer from zero. Every AT typed to see whether the module is alive puts off its return by that much. Take your hands off and wait <seconds>, and the module comes out by itself.

+OTAFWUP:ERROR,TIMEOUT,183253,408188,OVERRUN
ERROR:PAYLOAD_TIMEOUT

Only 183,253 of the image's 408,188 bytes arrived. Both numbers count only the image payload — the 96-byte header is not included, and this is not the size of the package file either. A timeout before the header has fully arrived (including when nothing arrived at all) is TIMEOUT,0,0, however much of the header came. The trailing OVERRUN means the port lost those bytes — the host sent everything. A timeout without OVERRUN is short with no sign of loss, so the host really did stop midway. If the port cannot keep up, use RTSCTS or lower the speed.

The most common refusal — PRODUCT​

+OTAFWUP:ERROR,PRODUCT,0x454F4501,0x454F4502
ERROR:INVALID_IMAGE

The first value is the package's, the second the module's. If they differ, the module writes nothing and refuses. The example above is a package of the SNMP product (0x454F4501) for the same hardware sent to the BACnet module (0x454F4502) — an intended refusal. A trailing ,OVERRIDDEN means the module's value comes from an AT+PRODUCTID override.

Check the module's value in the fourth field of AT+VERSION? (and whether it is overridden with AT+PRODUCTID?).

A string of ERROR:INVALID_COMMAND lines following a refusal is normal. The rest of the bytes already sent are being read as command lines; sending one empty line (CR) clears it up.

Port requirements​

On a 7-bit or XON/XOFF port the transfer does not start — either one corrupts the data silently instead of failing it, and that would show only in the CRC after hundreds of KiB had been sent. Change to 8 bits and one of NONE/RTSCTS/DTRDSR with AT+UART and try again. RTSCTS is not required, but it is recommended as a margin when raising the speed (GP6 module CTS ← host RTS, GP7 module RTS → host CTS).

With DTRDSR, start with DTR raised. The module erases the staging area, enters receive mode and starts the idle timer, and only then puts +OTAFWUP:READY in the transmit queue. If DTR is low, READY just stays in the queue, and a host waiting for READY sends nothing, so the transfer is abandoned after <seconds>. If DTR is raised after that, the host receives READY followed at once by +OTAFWUP:ERROR,TIMEOUT,0,0 and ERROR:PAYLOAD_TIMEOUT — the staging area has already been erased. The idle timeout ends this wait too.

+BACWRITE​

  • <type> is the short name (AO …); <prio> is the priority written, 1 … 16, for a commandable object, and 0 otherwise. <value> is in the same format as AT+BOBJ?, and a relinquish is NULL.
  • The confirmed form comes from objects with the F flag. <tid> is 1 … 65535. Answer with AT+BWRACK within 750 ms.
  • The notification form goes out only when any other write actually changed something (for a commandable object, the value of the slot written or the set of active slots; otherwise the Present_Value). A supervisory controller that writes the same value again produces no line.
  • +BACWRITE is never dropped. Writes from the network are unauthenticated and can come faster than the UART drains, so these lines are sent leaving room for command responses. If there is no room, the confirmed form answers the client at once with a NO_SPACE_TO_WRITE_PROPERTY error (the host never saw the question), and the notification form is left on the object as "notification pending" and sent when room frees up — writes arriving in between merge into one, and the line that goes out late carries the value now in effect and its command priority. The counts are in +DIAG:BACNOTIFY.
  • A write to an Out_Of_Service object is committed only inside the device, and the host is neither asked nor told (the reason for putting an output OOS is to try commanding it without moving the equipment). When OOS clears, an output or Value object whose Present_Value changed in the meantime reports the current value and command priority (0 if it is the Relinquish_Default or the object is not commandable) in one notification-form line, so that the host follows again.

Other BACnet URCs​

  • +BACDCC · +BACREINIT · +BIPFD · +BSC · +TIME:* do not wait, and do not use the room kept for command responses. If there is no room, the line is discarded (not sent again). The number discarded is counted by the last field of each line in §15 — +DIAG:BSCMSG for +BSC, +DIAG:BIPFD for +BIPFD, +DIAG:TIME for +TIME:*, +DIAG:BACDM for +BACDCC. These lines are discarded before they are formatted, so they are not in the dropped count of +DIAG:ATTX. If a count went up, the host reads the state again — AT+BIPFD?, AT+BSCSTATUS?, AT+TIME?, and for DCC the leading fields of +DIAG:BACDM. +BACREINIT is not counted, because a restart follows right after — the +READY and +DIAG:RESET of the next boot are its trace.
  • The restart after +BACREINIT drains the AT transmit queue for up to 500 ms, then closes the connections and resets. The Last_Restart_Reason of the next boot is COLDSTART or WARMSTART, as requested.
  • +BIPFD — a FAILED identical to the last one reported (same reason and code) is not sent again (so that a stopped BBMD does not produce a line on every retry). When the B/IP socket closes during registration or while registered (mode change · link · address change), +BIPFD:FAILED,NO_SOCKET; when it reopens and registers, +BIPFD:REGISTERED. Saving new settings forgets what was reported.
  • +BSC — nothing is output before the first connection attempt has ended. After that, there is one line when the state changes, and one when, with no connection, the device's reason becomes different from the one last reported and the reason of either URI has changed. A hub that keeps refusing with the same reason, or a primary and failover failing in turn with two different reasons (each URI's reason stays the same and only the device's reason swings between the two), does not produce a line every round. The BACnet task samples the state every cycle and outputs from that, so a connection that dropped and reconnected within one cycle produces no line — the record of it is the attempts · connects of AT+BSCSTATUS?. Discarded lines are the last field of +DIAG:BSCMSG.
  • +TIME:SNTPFAIL reasons: DNS (the server name did not resolve), TIMEOUT (no answer, or no ARP answer), BADREPLY (a response that is not the answer to the request — forged, stale, an unsynchronized server, or a server that says it is synchronized but gives a time before 2026: an answer the clock cannot be set from), NO_SOCKET (no hardware socket), SEND (the request could not even be sent — a failure on this side, in bind or send). It goes out only when the state changes, not on every attempt.

17. Common pitfalls​

  1. Forgetting AT+SAVE. BACnet settings have no effect on the network before they are saved, and without a save they are gone at the next boot. The same goes for object definitions made with AT+BOBJADD.
  2. Looking for the device without setting a mode. In the factory state AT+BACMODE is OFF, so nobody answers Who-Is. AT+BACMODE=BIP and AT+SAVE come first.
  3. AT+IP? differs from the value just set. That is normal — the query gives the chip's current value (§5).
  4. Putting your own company's name on WIZnet's Vendor ID (1697). The three are one statement. When shipping the module as your own product, put in your own ASHRAE Vendor ID, company name and model name together with AT+BACVENDOR; otherwise leave the defaults as they are.
  5. Putting a value into a commandable object with AT+BOBJVAL. It is ACCESS_DENIED — the Present_Value is decided by the network's priority array. The host can only report the status (,OK/,FAULT).
  6. Answering the +BACWRITE of a CONFIRMED object late. The deadline is 750 ms. Past it, the client has already received an error and AT+BWRACK is HOST_TIMEOUT. If the host cannot decide that fast, use the notification form instead of F and let the host follow the result.
  7. Running AT+BMAPRELOAD · AT+BMAPCLEAR · a web CSV import in the middle of editing. When they change the mapping, they save the whole configuration, so other unsaved settings go into flash too. An AT+BMAPRELOAD of the same CSV as the stored mapping saves nothing, but instead discards unsaved AT+BOBJADD · AT+BOBJDEL edits (§9). Either way, AT+SAVE first.
  8. AT+BMAPRELOAD gives CSV_NOT_AVAILABLE after an OTA. That is normal — the firmware image took the place of the stored CSV. The object definitions remain; to load the CSV again, upload it again. Keep the original CSV on the host side.
  9. Setting SC to STRICT and leaving the time source at BACNET. It is a deadlock combination and is refused. To use STRICT, first put in AT+TIMESRC=SNTP,"<server>" (or BOTH).
  10. Setting the B/IP port to 50003. It shares one port space with the web UI's TCP port and is refused.
  11. Reversing the sign of the UTC offset. A number uses the BACnet sign (west positive, Korea -540); quoted text uses the ISO sign ("UTC+09:00"). The query shows both.
  12. Giving up while waiting for the answer to the last AT+BSCCERTW chunk. Verification and writing can take up to a little over 15 seconds. If the answer was lost, send the same chunk again unchanged — the first answer is given again.
  13. Getting CRLF and data mixed up in binary mode. Every byte inside the payload is data. Send exactly the declared length. The result line comes on the same line as > .
  14. Judging a UDP channel to have failed because it is not ESTABLISHED. OPEN is normal for UDP (§11).
  15. Adding surplus arguments. Beyond the maximum number the command can take, it does nothing and refuses. Queries are the same — AT+BOBJ?x is ERROR:INVALID_PARAMETER. AT+SOCKOPEN, whose count differs by form, is counted against the count of that form (§3.2).
  16. Reading a query response as a URC. +BIPFD:STATE,… · +BIPFD:CONFIG,… are query responses, +BIPFD:REGISTERED,… · +BIPFD:FAILED,… are URCs. +TIME: has four fields as a query response and three as a URC.
  17. Sending credentials or firmware on a 7-bit or XON/XOFF port. The transfer does not even start: NOT_SUPPORTED. Change to 8 bits · NONE/RTSCTS, or use the web UI.
  18. AT+SOCKSEND on a UDP channel without AT+SOCKPEER. It is ERROR:NOT_CONNECTED, with no prompt — meaning there is no recipient. Use AT+SOCKPEER first, or AT+SOCKSENDTO (§11).
  19. Writing the queried instance back into AT+BACDEV to change only the name. The derived instance turns into a fixed number. Use AT+BACDEV=DEFAULT,"<name>" (§6).
  20. Trying to change the lease's DNS with AT+DNS on a DHCP network. If the lease gives a DNS, that one is used. AT+DNS is the fallback server for when the lease gives no DNS (§5).
